# Build de Skills e descoberta real pela Helena

Este documento explica como uma Skill sai do código-fonte em `src/skills` e se torna algo que Helena consegue descobrir, validar, carregar e executar de verdade — não apenas em testes com fixtures.

## O problema que existia

`tsc` compila apenas arquivos `.ts`. Cada Skill, porém, também possui um arquivo `skill.manifest.json` — um arquivo estático, sem código, que `FileSystemSkillDiscovery` lê diretamente do disco para descobrir Skills. Como `skill.manifest.json` nunca é importado por nenhum arquivo `.ts` (ele é lido como texto em tempo de execução, não via `import`), o TypeScript não tinha motivo para copiá-lo para `dist/`, e não copiava. O resultado: depois de `npm run build`, `dist/skills/maria-copywriting/` e `dist/skills/joao-marketing-strategy/` continham todo o JavaScript compilado, mas nenhum `skill.manifest.json`. Se `FileSystemSkillDiscovery` fosse apontada para `dist/skills` (o único lugar onde o entrypoint `./index.js` realmente existe como JavaScript executável), ela encontrava zero Skills. Se fosse apontada para `src/skills` (onde o manifesto existe), ela encontrava o manifesto, mas o `FileSystemSkillModuleLoader` falhava ao tentar importar `./index.js`, porque em `src/skills` só existe `index.ts`. Ou seja: não havia nenhum diretório único onde manifesto e entrypoint compilado coexistissem. Os testes de Helena nunca pegaram esse problema porque usam `tests/fixtures/skills/*`, uma pasta com manifestos e Skills de teste escritas diretamente em `.mjs`, sem depender de nenhum build.

## Como foi corrigido

A correção não mexeu em Helena nem no loader — ambos já estavam corretos e genéricos. O problema era puramente de empacotamento: faltava um passo de build que copiasse os manifestos estáticos para o mesmo diretório de saída do código compilado. Esse passo foi adicionado como um script Node dedicado, `scripts/copy-skill-manifests.mjs`, executado automaticamente depois do `tsc` como parte de `npm run build`.

O script percorre `src/skills` recursivamente. Para cada arquivo chamado exatamente `skill.manifest.json`, ele recria o mesmo caminho relativo dentro de `dist/skills` e copia o arquivo para lá — preservando a estrutura de pastas de cada Skill (`dist/skills/<id-da-skill>/skill.manifest.json`, ao lado do `index.js` que o `tsc` já colocou ali). Diretórios cujo nome começa com `_` são ignorados pelo próprio script, usando o mesmo critério padrão que `FileSystemSkillDiscovery` já usa para não carregar templates (`_template`). O script não conhece "Maria" nem "João" — ele não tem nenhuma lista fixa de Skills. Qualquer pasta nova dentro de `src/skills` que siga o padrão (um `skill.manifest.json` ao lado de um `index.ts` cujo `runtime.entrypoint` seja `./index.js`) é automaticamente coberta, sem precisar editar o script.

## Como funciona o build completo hoje

`npm run build` agora executa dois passos em sequência: `tsc -p tsconfig.json`, que compila todo `src/**/*.ts` para `dist/`, seguido de `npm run build:copy-skill-manifests`, que roda `scripts/copy-skill-manifests.mjs`. Ao final, `dist/skills/<id-da-skill>/` contém tanto o JavaScript compilado quanto o `skill.manifest.json` — exatamente o que `FileSystemSkillDiscovery` e `FileSystemSkillModuleLoader` precisam para descobrir e carregar a Skill de verdade. `npm test` já rodava `npm run build` antes dos testes, então o passo de cópia acontece automaticamente antes de qualquer teste também.

## Como a Helena descobre Skills reais

Em produção local (ou em qualquer script de composição futuro, como um CLI), a receita é: aponte `FileSystemSkillDiscovery` para `dist/skills` (nunca para `src/skills`), aponte `FileSystemSkillModuleLoader` para receber o pacote de dependências injetáveis que as Skills reais precisam (`{ valentina, clara, icaro, ... }`), rode `npm run build` antes de instanciar qualquer coisa, e chame `helena.discoverAndLoadSkills()`. A partir daí, `helena.findSkillByCapability(...)` e `helena.executeSkill(...)` funcionam com Skills reais exatamente como já funcionavam com as Skills de teste em `tests/fixtures/skills`. Isso foi corrigido de forma agnóstica ao arquivo de configuração: `src/config/zuno.config.example.json` foi atualizado para refletir isso, com `skills.directory` apontando para `dist/skills`.

### Sobre o pacote de dependências injetáveis

`FileSystemSkillModuleLoader` recebe, no construtor, um único objeto `runtimeDependencies` e repassa esse mesmo objeto para a fábrica `createSkill(dependencies)` de **qualquer** Skill descoberta. Cada Skill lê apenas as chaves que lhe interessam: Maria lê `dependencies.icaro`; João lê `dependencies.valentina`, `dependencies.clara` e, opcionalmente, `dependencies.icaro`. Isso já era genérico antes desta correção e continua sendo — não foi necessário alterar essa parte do loader. Também confirmei que uma Skill carrega com sucesso mesmo recebendo um `runtimeDependencies` vazio (`{}`): tanto Maria quanto João possuem, em sua fábrica `createSkill`, substitutos que lançam erro apenas quando o método da porta ausente é efetivamente chamado durante `execute()`, nunca durante o carregamento. Ou seja, `helena.discoverAndLoadSkills()` sempre consegue colocar uma Skill em estado `READY` independentemente de quais dependências reais foram fornecidas; só a execução de fato exige as dependências obrigatórias.

## Validação da descoberta real

Além dos testes automatizados, existe um script de diagnóstico, `scripts/verify-skills-discovery.mjs`, disponível via `npm run architecture:check`. Ele builda o projeto, instancia Helena com descoberta e carregamento reais apontados para `dist/skills`, e verifica: quantas Skills foram descobertas; se nenhuma delas é uma Skill de template; se nenhuma ficou em estado `FAILED`; e se as capabilities esperadas (`copywriting` → Maria, `strategy` → João, `marketing_strategy` → João) resolvem para a Skill certa. Ele imprime um relatório legível no terminal e termina com código de saída diferente de zero se qualquer verificação falhar, podendo ser usado como gate de CI no futuro.

## Como criar uma nova Skill sem quebrar o build

Nenhum passo novo foi adicionado ao fluxo de criação de Skills. Basta seguir o padrão já usado por Maria e João: criar uma pasta em `src/skills/<id-da-skill>/` (sem prefixo `_`) contendo um `skill.manifest.json` com `runtime.entrypoint: "./index.js"`, um `index.ts` que exporta `createSkill`, e a implementação da Skill. Ao rodar `npm run build`, o `tsc` compila o `.ts` normalmente e `copy-skill-manifests.mjs` copia o `skill.manifest.json` para o mesmo lugar automaticamente, sem exigir nenhuma edição em `scripts/copy-skill-manifests.mjs`, em Helena ou no loader. A próxima Especialista (Sofia) só precisa seguir essa mesma estrutura de pasta para ser descoberta corretamente.

# Zuno

Zuno é a fundação de uma Agência de Marketing Inteligente composta por especialistas em Inteligência Artificial. O modo oficial desta fase é `LOCAL_PRODUCTION`: execução 100% local via VS Code/CLI, sem painel web, servidor, banco de dados, CDN ou integrações externas reais. Neste modo, imagens usam Developer Assisted Mode e vídeos são renderizados automaticamente em local (FFmpeg via `VideoRenderingPort`, motion graphics — ver `docs/video-rendering.md`), agora com resolução automática de assets visuais por cena via `VisualAssetResolverPort` (biblioteca local, provedor gratuito por manifesto e Developer Assisted Mode para imagens faltantes — ver `docs/visual-asset-resolver.md`); todos os artefatos ficam em `artifacts/<executionId>/` e a Ana apenas prepara payload local (`local_ready`/`dry_run`), sem publicar na Meta e sem acionar hospedagem pública. O objetivo deste repositório é estabelecer uma arquitetura preparada para crescimento, baixo acoplamento e separação rigorosa de responsabilidades.

O CEO conceitual do projeto se chama Zuno. Zuno representa a identidade da agência, mas não executa tarefas operacionais. A coordenação de trabalho pertence ao Arthur, o Diretor de Operações e orquestrador. Arthur decide quais Skills devem trabalhar, em qual ordem e quais informações cada uma recebe, sem criar conteúdo, sem gerar imagens, sem publicar e sem conversar diretamente com APIs externas.

Esta base foi estruturada com Clean Architecture, SOLID e contratos explícitos para permitir que futuras Skills sejam adicionadas sem reescrever o núcleo do sistema.

## Plataforma nova (Conversation → Operations)

Além do pipeline `LOCAL_PRODUCTION` descrito abaixo, este repositório contém, desde a Sprint 08, uma segunda arquitetura completa — uma API HTTP (Fastify, `/v1`) multi-tenant com RBAC + frontend Next.js, cobrindo Conversation, Briefing, AI Gateway, Planning, Runtime, Execution, Publication (com outbox/dispatch/reconciliação), Credential/Governance/Compliance, Webhooks, Scheduling/Calendário Editorial, Analytics e uma camada Operacional transversal (Production Guard, circuit breakers, health/readiness, backpressure, rate limiting). As duas arquiteturas nunca se importam entre si (`npm run architecture:check` garante isso). **Production permanece bloqueada por padrão** nesta plataforma nova — ver `docs/sprint-24-final-report.md` (certificação de Release Candidate 1.0) e:

- `docs/architecture.md` — visão C4 (contexto/containers/componentes) e mapa de domínios
- `docs/event-catalog.md` — todos os eventos, origem, consumidores, versionamento, idempotência
- `docs/contract-catalog.md` — Ports, Adapters, Repositories, Policies
- `docs/runbook.md` / `docs/troubleshooting.md` / `docs/deployment.md`

Rodar localmente: `npm run zuno:api` (API) e `cd web && npm run dev` (frontend).

## Estado atual

O projeto contém estrutura, documentação, contratos, portas arquiteturais, Arthur como planejador de execução, Helena como gerente de Skills, Caio como executor de Workflows, Valentina como Gerente de Clientes, Clara como Centro de Conhecimento, Eduardo como Skill de planejamento editorial, João como Skill de estratégia de marketing, Maria como Skill de copywriting, Sofia como Skill de direção de arte, Bianca como Skill de design para redes sociais, Pedro como Skill de geração de imagens, Lucas como Skill de revisão de qualidade, Ana como Skill de publicação social, Bruno como Skill de estratégia e roteirização de vídeos curtos, Vanessa como Skill de direção de vídeo, Diego como Skill de edição de vídeo, Rafa como Skill de renderização/geração de vídeo e Ícaro como cérebro central de comunicação com IA. Não existe integração concreta com OpenAI, Google, banco de dados, servidor ou SaaS; a integração com Meta/Instagram existe como adaptador real (`src/infrastructure/social-networks`), mas ainda sem credenciais configuradas.

O projeto já possui um ponto de entrada real: uma CLI local (`npm run zuno -- "<comando>"`, em `src/interfaces/cli`) que percorre o fluxo completo Arthur → Caio → Helena → Skills a partir de um único comando em texto. Caio encadeia automaticamente a saída de cada etapa na entrada da próxima (via `inputBindings` do `ExecutionPlan`, resolvidos por `resolveStepInput`) — nenhuma Skill precisa ser chamada manualmente entre uma etapa e outra. Quando o plano inclui uma etapa `human_gate`, o workflow pausa em `WAITING_HUMAN_APPROVAL` e pode ser retomado depois, inclusive em um novo processo, via `Caio.resume()`/`--approve`/`--reject` (a CLI persiste e recarrega a execução com `hydrateExecution`). Antes de executar qualquer etapa, Caio também verifica se toda capability exigida pelo plano tem Skill pronta em Helena; se faltar alguma (ex.: `campaign_management`, ainda não implementada), o workflow falha imediatamente com uma mensagem consolidada, sem gastar chamadas de IA em etapas anteriores. Um carrossel não é uma dessas capabilities reservadas: é apenas `image_generation` com `imageCount > 1`, decisão que agora é exclusiva do Eduardo (via Editorial Brief) — Arthur nunca planeja uma etapa separada para "criar carrossel" e também deixou de decidir sozinho o formato final do conteúdo.

A experiência da CLI agora é natural-first: o usuário escreve pedidos como "crie um post", "crie um carrossel com 5 imagens", "crie uma imagem", "crie um vídeo para Reels", "crie um TikTok", "crie um Story" ou "crie um anúncio", sem citar Arthur, Helena ou qualquer Skill. Arthur monta o plano e decide qual pipeline estrutural entra nele (imagem ou vídeo), mas quem decide o formato final, a quantidade de slides/telas, a duração do vídeo, a emoção principal, a estrutura narrativa, o CTA, a profundidade, a complexidade e a prioridade de conversão é o Eduardo, sempre a primeira etapa do plano. A Ana só entra quando houver um pedido explícito de publicar/postar/agendar; citar Instagram, Facebook ou outro canal apenas define o canal da peça. Se nenhum modo for informado, a CLI usa `LOCAL_PRODUCTION`. Quando o workflow termina, a CLI gera uma entrega final padronizada em `artifacts/<executionId>/index.html`, reunindo preview, downloads reais, `caption.txt`, `hashtags.txt`, `metadata.json`, `execution-report.json`, botões de copiar legenda/hashtags/CTA, estatísticas, validações, warnings e relatório das Skills executadas para imagem, carrossel ou vídeo.

Arthur transforma um comando em texto em um `ExecutionPlan`. Ele não executa o plano, não chama Skills e não acessa providers externos.

Helena gerencia as Skills. Ela descobre manifestos, valida, carrega, registra no Registry, localiza por capability e executa uma Skill somente quando solicitada por Arthur. Helena também não cria conteúdo, não publica e não chama providers externos de marketing.

Caio executa workflows. Ele recebe um `ExecutionPlan` criado por Arthur, percorre as etapas, chama Helena quando uma etapa exige Skill, pausa em aprovação humana e retorna um relatório estruturado. Caio não altera o plano e não conversa com providers externos.

Valentina administra clientes, planos, limites, consumo, permissões, integrações futuras e assinatura. Todo workflow precisa estar associado a um cliente resolvido por Valentina.

Clara centraliza conhecimento de clientes, marcas, produtos, campanhas, identidade, público, conteúdo, preferências de IA e contexto de workflows. Nenhum Especialista deve armazenar conhecimento próprio ou acessar arquivos diretamente; o acesso acontece por `ClaraKnowledgePort`.

Campaign Manager é o módulo que organiza uma campanha completa a partir de um único objetivo em texto ("Quero uma campanha para divulgar o Rumo ao Altar durante 30 dias.", "Quero uma campanha para captar casais recém-noivos.", "Quero uma campanha para divulgar a lista de presentes."). **Não é uma Skill e não participa do `ExecutionPlan`: funciona acima do Arthur**, chamando `arthur.planFromText` sob demanda para cada conteúdo — nunca o contrário. Gera um Campaign Plan com objetivo, duração, persona, canais, frequência, calendário sugerido e uma lista de conteúdos, cada um com formato recomendado, prioridade, CTA e relação com os demais (todo conteúdo referencia a abertura da campanha). Campaign Manager não cria copy, imagem ou vídeo — cada conteúdo pode gerar, sob demanda, um `ExecutionPlan` independente pelo Arthur. Mantém histórico de campanhas, status por conteúdo (pendente, plano gerado, em revisão, aprovado, rejeitado, publicado, falho), percentual concluído e contagens (documentado em `docs/campaign-manager.md`).

Quality Feedback é o módulo de ciclo de melhoria contínua do Zuno — **não é uma Skill**: não possui manifesto, não é descoberto por Helena e nunca participa de um `ExecutionPlan`. Depois que uma execução termina, o usuário pode avaliá-la (estrelas de 1 a 5 ou nota de 1 a 10), marcar quais aspectos precisam melhorar (estratégia, copy, legenda, CTA, hashtags, layout, design, hierarquia visual, imagem, vídeo, roteiro, tempo, Reels ou qualidade geral) e escrever um comentário livre; tudo fica armazenado localmente (`.zuno-data/quality-feedback.json`), junto com `executionId`, cliente, tipo de conteúdo, formato e Skills utilizadas. Um relatório local (`npm run zuno -- --quality-report`) mostra média geral, média por Skill, por formato e por campanha, evolução ao longo do tempo, conteúdos mais/menos bem avaliados e reclamações recorrentes. O Eduardo consulta esse histórico (dependência opcional, mesmo padrão do Ícaro) antes de montar um novo Editorial Brief — mas o feedback nunca decide nada sozinho, só acrescenta recomendações a `recommendationsForJoao` (documentado em `docs/quality-feedback.md`).

Eduardo é a Skill de planejamento editorial do Zuno e a primeira etapa de todo `ExecutionPlan`, antes até do João. Ele recebe apenas a solicitação do usuário e decide a melhor estratégia de conteúdo — formato (imagem única, carrossel, Reels, vídeo ou Story), quantidade recomendada de slides/telas, duração recomendada quando for vídeo, emoção principal, estrutura narrativa, CTA recomendado, nível de profundidade, complexidade e prioridade de conversão —, consultando Valentina para identificar o cliente, Clara para obter marca/público/conteúdo e, de forma opcional, Ícaro para aprimorar apenas a justificativa, a estrutura narrativa, a emoção principal e as recomendações (nunca o formato, a quantidade, a duração, o canal ou o CTA, que permanecem inteiramente heurísticos). Eduardo não cria copy, imagem ou vídeo e não define layout, paleta ou tipografia; ele monta o Editorial Brief estruturado que orienta o João (documentado em `docs/eduardo-editorial-planning.md`).

João é a primeira Skill de estratégia do Zuno. Ele transforma uma solicitação de marketing — agora orientada pelo Editorial Brief do Eduardo — em uma estratégia estruturada, consultando Valentina para identificar o cliente, Clara para obter contexto e, de forma opcional, Ícaro para aprimorar a estratégia. João monta o briefing estruturado que orienta a Maria e o briefing preliminar que orienta a Sofia.

Maria é a Skill de copywriting do Zuno. Ela transforma briefings estruturados em copies estruturadas usando apenas a abstração `IcaroBrainPort`.

Sofia é a Skill de direção de arte do Zuno. Ela transforma a estratégia do João em uma direção visual estruturada — conceito criativo, identidade visual, paleta de cores, tipografia, moodboard, estilo, linguagem estética, referências de design e a emoção que o material deve transmitir —, consultando Valentina para identificar o cliente, Clara para obter identidade visual e contexto de marca e, de forma opcional, Ícaro para aprimorar a direção. Sofia não gera imagens e não define layout; ela monta o briefing estruturado que orienta a Bianca.

Bianca é a Skill de Design para Redes Sociais do Zuno. Ela transforma a direção de arte da Sofia em um layout extremamente detalhado — grid, hierarquia visual, alinhamentos, espaçamentos, margens, peso visual, tamanho de títulos e textos, cards, ícones, botões, boxes, separadores, sombras, bordas, estilo de ilustrações e de mockups, posicionamento de logo, área de respiro, ponto focal de cada slide e sequência/consistência do carrossel —, consultando Valentina para identificar o cliente, Clara para obter identidade visual e regras de publicação e, de forma opcional, Ícaro para aprimorar apenas grid, hierarquia, aplicação de cor e estilo de componentes. Bianca não cria estratégia, não escreve copy, não gera imagens e não define conceito criativo, paleta ou tipografia — isso continua sendo exclusivo da Sofia. Bianca monta o briefing estruturado e detalhado que orienta o Pedro.

Pedro é a Skill de geração de imagens do Zuno e a primeira a produzir um artefato visual de verdade. Ele transforma o briefing de design da Bianca em uma imagem ou conjunto de imagens, consultando Valentina para identificar o cliente e Clara para obter identidade visual, marca e publicação. A origem dos pixels depende do modo configurado: por padrão (`ai_provider`) pede a geração ao Ícaro; no modo oficial da CLI local (`developer_assisted` — não existe geração de imagem nativa no Claude Code nem provider externo configurado nesta fase), monta um prompt técnico e o caminho exato onde a imagem deve ser salva, e aguarda a IA desenvolvedora criar o arquivo real em disco antes de continuar (ver `docs/pedro-image-generation.md`). Pedro deixou de tomar qualquer decisão de layout — ele apenas executa o que a Bianca especificou. Pedro não publica; ele cria artefatos estruturados (`SkillArtifact`, com suporte a imagem única ou carrossel) prontos para revisão de qualidade e para futuras Skills de publicação.

Lucas é a Skill de revisão de qualidade do Zuno. Ele revisa o pacote completo produzido por João, Maria, Sofia, Bianca e Pedro — estratégia, copy, direção visual, design e imagens — validando coerência, tom de voz, CTA, regras da marca e riscos, e devolve um status de revisão (`approved`, `approved_with_warnings`, `needs_adjustments` ou `rejected`) junto com um score, um checklist e sugestões de ajuste. Quando o comando aciona a pipeline de vídeo, Lucas também revisa o pacote de vídeo completo — roteiro do Bruno, direção audiovisual da Vanessa, plano de edição do Diego e vídeo final do Rafa — validando coerência entre as quatro etapas, duração, formato vertical, proporção 9:16, presença e consistência do CTA, clareza do gancho inicial, ritmo, legibilidade dos textos na tela e qualidade técnica mínima do arquivo de vídeo, no mesmo checklist e com os mesmos status. Arthur conecta a Revisão à etapa de renderização de vídeo automaticamente quando ela existe no plano, sem alterar o comportamento da pipeline de imagens. Lucas nunca corrige nada por conta própria; ele apenas aponta problemas antes da aprovação humana.

Ana é a Skill de publicação social do Zuno, responsável nesta fase apenas por preparar publicação orgânica no Instagram e no Facebook. Ela recebe o pacote completo já revisado pelo Lucas e a confirmação de aprovação humana, valida as regras obrigatórias (cliente, integração conectada, copy válida, imagem/carrossel do Pedro ou vídeo do Rafa válido, aprovação do Lucas, aprovação humana, canal e recurso liberados no plano, compatibilidade do provider e regras de publicação da Clara) e monta o payload. Em `LOCAL_PRODUCTION`, mesmo quando o comando pede publicação, Ana retorna `local_ready`, mantém caminhos locais no payload, não chama `SocialPublisherPort`, não agenda, não faz upload e não aciona `ArtifactHostingPort`. Em uma fase futura, `publish_now` ou `schedule` exigirão URLs públicas antes de chamar um provider real. Ana não usa Inteligência Artificial, não conversa com o Ícaro e nunca acessa a API da Meta diretamente.

Bruno é a primeira Skill da pipeline de vídeo própria do Zuno (João → Bruno → Vanessa → Diego → Rafa → Lucas → Ana quando houver pedido explícito de publicação). Ele transforma a estratégia de marketing do João diretamente em um roteiro de vídeo curto profissional para Reels, TikTok, Shorts e vídeos verticais — estrutura narrativa, gancho, cenas com texto falado, texto na tela, B-roll, enquadramento, movimento de câmera, ritmo, pausas, transições e efeitos sonoros, além de sugestões de trilha, CTA final e observações de gravação e edição —, consultando Valentina para identificar o cliente, Clara para obter marca e público e, de forma opcional, Ícaro para aprimorar o roteiro. Bruno não gera, edita, renderiza ou publica vídeo, e não define layout de peças visuais estáticas; ele monta o briefing estruturado que orienta a Vanessa.

Vanessa é a segunda Skill da pipeline de vídeo, posicionada depois do Bruno. Ela transforma o roteiro de Bruno em uma direção audiovisual completa — mapa de cenas, enquadramentos, composição visual por cena, movimentos de câmera, ritmo visual, transições, estilo de legenda na tela, efeitos visuais e sonoros sugeridos, trilha recomendada, orientação de B-roll, direção de luz, direção de cor e orientação de gravação/edição —, consultando Valentina para identificar o cliente, Clara para obter identidade visual e, de forma opcional, Ícaro para aprimorar a direção. Vanessa não cria roteiro (isso é exclusivo do Bruno), não edita, renderiza ou publica vídeo, e não cria imagens finais; ela monta o briefing estruturado que orienta o Diego.

Diego é a terceira Skill da pipeline de vídeo, posicionada depois da Vanessa. Ele transforma o roteiro de Bruno e a direção audiovisual de Vanessa em um plano técnico de edição completo — timeline, ordem das cenas, cortes, duração de cada trecho, legendas por cena, textos na tela, transições, efeitos visuais e sonoros, trilha sugerida, assets necessários, instruções de edição e checklist técnico —, consultando Valentina para identificar o cliente, Clara para obter identidade visual e, de forma opcional, Ícaro para aprimorar o plano. Diego não cria roteiro, não dirige vídeo (isso é exclusivo de Bruno e Vanessa), não renderiza nem publica vídeo, e não gera vídeo final; ele monta o briefing estruturado que orienta o Rafa.

Rafa é a quarta Skill da pipeline de vídeo, posicionada depois do Diego. Ele transforma o plano técnico de edição de Diego em um MP4 real — prompt técnico final, caminho esperado do arquivo final, especificações técnicas (formato, resolução, duração, proporção, fps, codecs), assets necessários e instruções finais de renderização. Desde a v1.1, Rafa **prefere renderização automática local**: uma nova porta de aplicação, `VideoRenderingPort`, implementada por `FfmpegVideoRenderingAdapter` (`src/infrastructure/video-rendering/`), roda o FFmpeg localmente (nunca uma API externa, nunca dentro da Skill — Rafa só conhece a interface) e produz motion graphics reais com imagem por cena, texto, legendas, CTA, logo, transições, zoom/pan e música local a partir da timeline de Diego — ver `docs/video-rendering.md`. Antes de renderizar, Rafa consulta `VisualAssetResolverPort`, que usa a intenção visual de Vanessa/Diego para escolher assets reais da biblioteca local/provedor por manifesto; quando não encontra imagem adequada, o workflow pausa com `pendingVisualAssets` e caminho exato em `artifacts/<executionId>/visual-assets/scene-XX.png`, sem usar placeholder. Developer Assisted Mode também continua existindo para o MP4 final quando a renderização automática falha. Em ambos os casos, o artefato só é registrado depois de validado. Rafa não cria roteiro, não dirige vídeo, não edita o conteúdo conceitualmente e não publica. Arthur já reconhece as capabilities `video_script`, `video_direction`, `video_editing` e `video_rendering` e inclui as etapas "Roteiro de vídeo", "Direção de vídeo", "Edição de vídeo" e "Renderização de vídeo" no plano em cascata quando o comando menciona um roteiro, sem alterar a pipeline de imagens. A publicação desse artefato agora passa pela mesma Ana/capability `social_publishing`, que diferencia `mediaType: "video"` no payload, em qualquer um dos dois modos de geração.

Ícaro centraliza toda comunicação com IA. Especialistas conversam com Ícaro, e Ícaro conversa com Providers por `AIProviderPort`, selecionando Provider e Modelo, controlando retry, fallback, timeout, tokens, custos, logs e eventos.

## Execução local

O projeto é iniciado localmente, pelo VS Code ou por CLI. Instale as dependências, valide o projeto e rode um comando real:

```bash
npm install
npm run typecheck
npm test
npm run build
npm run zuno -- --mode local-production "crie um carrossel para Instagram sobre taxa zero no Rumo ao Altar"
npm run zuno -- "crie um post para o Rumo ao Altar no Instagram e Facebook"
npm run zuno -- --rate <executionId> --stars 4 --needs-improvement cta,hashtags --comment "CTA podia ser mais direto"
npm run zuno -- --quality-report --client-id client-rumo
npm run zuno -- --assets-scan
npm run zuno -- --assets-list
npm run zuno -- --assets-report
npm run zuno -- --music "assets/audio/music/musica.mp3" "crie um Reels sobre site oficial de casamento"
npm run zuno -- --campaign "Quero uma campanha para divulgar o Rumo ao Altar durante 30 dias." --client-id client-rumo
npm run zuno -- --campaign-show <campaignId>
```

`--mode local-production` é opcional porque `LOCAL_PRODUCTION` é o padrão atual. Se o workflow pausar em `WAITING_ASSISTED_GENERATION`, salve a imagem, o asset visual ou o vídeo no caminho indicado e retome com `npm run zuno -- --mode local-production --continue <executionId>`. Se pausar em `WAITING_HUMAN_APPROVAL`, retome com `npm run zuno -- --mode local-production --approve <executionId>` (ou `--reject`). `npm run zuno -- --list` lista execuções aguardando aprovação. Detalhes completos em `src/interfaces/cli/README.md`.

Ao concluir uma execução aprovada, abra o `index.html` listado no terminal. Essa página é a entrega oficial do material: imagens aparecem com preview grande e botões de baixar/abrir; vídeos aparecem com player HTML5 e botão de download; legenda, hashtags e CTA ficam disponíveis no próprio HTML com cópia por clipboard. A pasta também contém `caption.txt`, `hashtags.txt` quando houver hashtags, `metadata.json`, `execution-report.json`, imagens/vídeos e `carousel.zip` quando houver múltiplas imagens. Nada é publicado automaticamente em `LOCAL_PRODUCTION`; o material fica pronto para publicação manual.

`npm run build` compila todo `src/**/*.ts` para `dist/` e, em seguida, copia o `skill.manifest.json` de cada Skill real para o mesmo diretório de saída, preservando a estrutura de pastas. Isso é o que permite que `FileSystemSkillDiscovery` e `FileSystemSkillModuleLoader` encontrem e carreguem Skills reais (não apenas as fixtures de teste) a partir de `dist/skills`. Para validar essa descoberta real de ponta a ponta, rode `npm run architecture:check` — o script builda o projeto e confirma que cada Skill esperada é encontrada pela capability correta. Detalhes completos em `docs/skills-build-and-discovery.md`.

# Infraestrutura de IA

Espaço reservado para adaptadores futuros de modelos de IA. OpenAI, Gemini, Anthropic, modelos locais ou qualquer outro provedor deverão entrar aqui como implementações de `AIProviderPort`, nunca diretamente dentro das Skills.

Os Especialistas conversam apenas com o Ícaro por `IcaroBrainPort`. O Ícaro conversa com os Providers por `AIProviderPort`. Essa separação permite trocar provedores, modelos, política de custos, retry e fallback sem alterar Maria ou qualquer outro Especialista futuro.

## Geração de imagem do Pedro — três origens possíveis, nunca confundidas

O Zuno diferencia explicitamente três origens possíveis para uma imagem do Pedro. Nenhuma delas deve ser confundida com outra em código, log ou relatório:

1. **`ai_provider` com `DeterministicFakeIcaroProvider`** — fake, exclusivamente para testes automatizados (`tests/*.test.mjs`) e para exercitar o pipeline de artefatos em desenvolvimento. Nunca gera pixels reais: devolve bytes fictícios (`fake-image-bytes-slide-N`) codificados em base64. Identificável no relatório por `provider.id === "fake-icaro-provider"`. **Nunca usado pela CLI** em uso real.
2. **`ai_provider` com um provider real** — ainda não implementado nesta fase. Exigiria uma implementação concreta de `AIProviderPort` (`kind: "image"`) para um provedor real (ex.: OpenAI Images, Google Imagen, Stability AI) e uma credencial configurada. Nenhum destes existe hoje em `src/infrastructure/ai`.
3. **`developer_assisted`** — o modo oficial da CLI local (`src/interfaces/cli/run-command.ts`). Pedro nunca chama o Ícaro para pixels neste modo: monta um prompt técnico e o caminho exato onde a imagem deve ser salva (`artifacts/<executionId>/images/slide-01.png`), e sinaliza `needs_assisted_generation` até que o arquivo exista fisicamente em disco, verificado exclusivamente via `ArtifactDeliveryPort.readFile` (nunca por `child_process` ou qualquer execução de comando externo). Identificável no relatório por `provider.id === "developer-assisted"` e `generationMode: "developer_assisted"`.

**Por que existe o modo `developer_assisted` em vez de geração automática:** o Claude Code (o agente de desenvolvimento usado para construir e operar este projeto) **não possui nenhuma capacidade nativa de geração de imagem** — nem como ferramenta própria, nem como MCP oficial da Anthropic, nem como parte do modelo. Isso foi confirmado tecnicamente (busca completa no catálogo de ferramentas do agente + verificação contra a documentação oficial do Claude Code) e não deve ser assumido como disponível em nenhuma implementação futura sem nova verificação. Sem provider externo configurado (decisão explícita desta fase) e sem geração nativa disponível, a única forma de produzir uma imagem real localmente é a IA desenvolvedora (quem estiver operando o Claude Code na sessão) criar o arquivo diretamente, seguindo o prompt e o caminho que Pedro fornece — daí "Developer Assisted Mode". Ver `docs/pedro-image-generation.md` para o fluxo completo e `src/interfaces/cli/README.md` para o uso via CLI.

**O que foi removido desta pasta (histórico de segurança):** uma versão anterior chegou a incluir `CommandNativeDeveloperImageGenerator`, um adaptador que executava `child_process.spawn(command, { shell: true })` com o comando lido de uma variável de ambiente (`ZUNO_NATIVE_IMAGE_GENERATOR_COMMAND`), mais um fallback oculto que devolvia um PNG estático de 1×1 pixel transparente disfarçado de "imagem gerada". Esse código não foi escrito como parte do fluxo de trabalho documentado deste projeto, representava uma superfície de execução de comando arbitrário, e violava a regra de nunca apresentar um fake como imagem real. Foi removido por completo e substituído pelo Developer Assisted Mode descrito acima, que não executa nenhum comando externo — apenas lê arquivos que já existem em disco.
